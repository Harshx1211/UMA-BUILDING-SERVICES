### Adding Future Migrations

When you add a new column or table:

**In the app (SQLite):**
1. Increment `CURRENT_SCHEMA_VERSION` in `lib/database.ts`
2. Add a new `if (currentVersion < N) { ... }` block
3. Update `types/index.ts` if the column maps to a TypeScript interface

**In Supabase:**
1. Run the change directly in the SQL Editor
2. Refresh `supabase/schema.sql` afterward so it stays a true mirror of the live DB
3. Update the version table above and the SQLite version table below

## Local SQLite Schema

The SQLite database (`uma-building-services.db`) is created automatically by `lib/database.ts → initializeSchema()` on every app launch.

It **mirrors** the Supabase schema exactly, plus two SQLite-only tables:

| Table | Notes |
|-------|-------|
| `meta` | Key-value store — holds `schema_version` |
| `sync_queue` | Offline write queue — **never synced to Supabase** |

### SQLite Version History

The app uses a versioned migration system. Version is stored in `meta` (`key = 'schema_version'`).
Each `if (currentVersion < N)` block in `initializeSchema()` runs **exactly once** and is idempotent.

| Version | What Changed |
|---------|-------------|
| **0** | Initial schema — all core tables created |
| **1** | `users.push_token TEXT` — Expo push notification token |
| **2** | `job_assets.checklist_data TEXT`, `job_assets.is_compliant INTEGER` |
| **3** | `CREATE INDEX idx_job_assets_asset_id` — faster previous-result lookups |
| **4** | `sync_queue.retry_count INTEGER`, `sync_queue.last_error TEXT` — retry limiting |
| **5** | `assets.variant TEXT`, `assets.asset_ref TEXT` — asset sub-type and site reference |

> **Adding a new SQLite migration:**
> 1. Increment `CURRENT_SCHEMA_VERSION` in `lib/database.ts`
> 2. Add a new `if (currentVersion < N) { ... }` block following the existing pattern
> 3. Add the corresponding Supabase `ALTER TABLE` to `docs/supabase_migrations.sql`
> 4. Update the tables above in this file

### `sync_queue` Columns

| Column | Type | Notes |
|--------|------|-------|
| `id` | INTEGER PK | SQLite autoincrement |
| `table_name` | TEXT | Target Supabase table |
| `record_id` | TEXT | The record's UUID |
| `operation` | TEXT | `insert` \| `update` \| `delete` |
| `payload` | TEXT | JSON-stringified record |
| `synced` | INTEGER | `0` = pending, `1` = done, `-1` = permanently failed |
| `retry_count` | INTEGER | Incremented on each failed push (max 5) |
| `last_error` | TEXT | Last failure reason — useful for debugging |
| `created_at` | TEXT | ISO 8601 timestamp |

## Sync Architecture

```
User Action (e.g. Fail an Asset)
  │
  ▼
Zustand Store (updateAssetResult)
  │  writes immediately
  ▼
Local SQLite (upsertRecord → job_assets)
  │  queues write
  ▼
sync_queue table
  │
  ▼ (when online, every 60 s)
Background Sync Engine (lib/sync.ts)
  │  pushes pending items
  ▼
Supabase (Postgres) — REST API
```

**Key rules:**
- UI always reads from SQLite — never Supabase directly
- Supabase is append-only from the app's perspective; it never overwrites local state
- `upsertRecord()` uses `ON CONFLICT(id) DO UPDATE SET` — never `INSERT OR REPLACE` — to preserve FK child rows
- Items that fail 5+ pushes are marked `synced = -1` and abandoned (check `last_error`)

## Key Architecture Decisions

### Signature Storage
Signatures are uploaded to Supabase Storage (`job-photos/signatures/{job_id}/signature.png`).
Only the **public URL** is stored in `signatures.signature_url`. Base64 is never stored in the DB.

### Column Name Security
All generic CRUD helpers (`insertRecord`, `updateRecord`, etc.) validate column names via
`_safeColumnName()` before interpolating into SQL — prevents SQL injection via attacker-controlled keys.

### Asset Type System
Asset types are defined in `constants/AssetData.ts` — the single source of truth for:
- Official type names (must match `assets.asset_type` values in DB)
- Sub-variants per type
- Icons, colours, inspection routines
- Compliance checklist mapping (`constants/Checklists.ts`)
